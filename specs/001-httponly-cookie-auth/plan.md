# Implementation Plan: HttpOnly cookie session

**Spec**: [spec.md](spec.md) | **Research**: [research.md](research.md) | **Contracts**: [contracts/](contracts/) | **Quickstart**: [quickstart.md](quickstart.md)

## Summary
Move the session credential (JWT) from `localStorage` to an `HttpOnly` cookie set by the API. Services accept the cookie first and the explicit `Authorization` credential as a fallback. Add a real logout (cookie cleared + server-side revocation via a denylist). The Angular app stops handling the token and learns "signed in" by asking the server.

## Technical Context
- **Back end**: .NET 10; ASP.NET Core; MediatR; gRPC (Authentication, FileStorage); SignalR (Notifications); MassTransit broker; Redis or in-memory token cache (`Features` switch); tests NUnit + Moq + FluentAssertions.
- **Front end**: Angular 21, NgRx, `@microsoft/signalr`, `grpc-web`, NSwag client; tests vitest.
- **Unchanged**: `frontend-next/`, the persistence layer, the email-code login method.
- **Constraints**: all hosts share the site `petukhov.fyi`; front end is cross-origin to every service (CORS with credentials).

## Design Decisions

### D1. Resolve the credential once, in `JwtMiddleware` (FR-001..FR-004, FR-012)
- `API/LetsTalk.Server.API.Middleware/JwtMiddleware.cs`: token = cookie `auth-token` if present, else the last part of the `Authorization` header. Put the **bare** token in `HttpContext.Items["Token"]` and the account in `Items["AccountId"]`.
- `Applications/LetsTalk.Server.API/Controllers/ApiController.cs`: `GetToken()` returns `Items["Token"]`. `MessageController` is unaffected otherwise.
- Extract the cookie name into the existing configuration model (see D2) instead of a literal.
- **Invalid cookie must not break public endpoints (FR-013).** Today the middleware throws `UnauthorizedAccessException` for any invalid token (`JwtMiddleware.cs:24,28`), which `CustomExceptionMiddleware` turns into 401 even on anonymous endpoints. With cookies the client cannot clear a stale token, so sign-in and sign-out would be blocked. Rule: if the credential came from the cookie and validation fails (null account id or `RpcException`), do **not** throw; call `Response.Cookies.Delete` (same Domain/Path) and continue without `AccountId`; the custom `[Authorize]` filter then returns 401 on protected endpoints. If the credential came only from the header, keep today's throw. Precedence: a valid cookie wins over an invalid header. Exception: if the Authentication service is unreachable (`Unavailable`/`DeadlineExceeded`), continue anonymously but keep the cookie, so an outage does not sign users out. The cookie helpers (`AppendAuthCookie`/`DeleteAuthCookie`, parsing `SameSite`) live in `API/LetsTalk.Server.API.Middleware/AuthCookieExtensions.cs`.

### D2. Login sets, logout clears the cookie (FR-002, FR-005)
- New settings class `AuthCookieSettings` (`Name`, `Domain`, `Secure`, `SameSite`) in `Infrastructure/Configuration/LetsTalk.Server.Configuration/Models/` next to `SecuritySettings.cs`, bound from config section `AuthCookie` (`services.Configure<AuthCookieSettings>(configuration.GetSection("AuthCookie"))` in each service's registration, as for the other settings; defaults in the class, so no `appsettings.json` change). Used by both the API (set/clear) and, for the cookie name, by Notifications and File storage (read), so the name is defined once.
- `AuthenticationController.EmailLoginAsync`: after the command succeeds with `Success`, append the cookie (`HttpOnly`, `Expires` = JWT expiry). Response body no longer carries the token: remove `Token` from `Models/LetsTalk.Server.Models.Dtos/LoginResponseDto.cs` and stop setting it in `EmailLoginCommandHandler`. Expiry: the handler returns the token only to the controller through the command result (`EmailLoginResult(Token, ExpiresAt)` in `API.Core.Commands`) so the DTO stays clean. The expiry comes from the Authentication service: `GenerateJwtTokenResponse` gets `expires_at_unix_seconds` (see `contracts/auth-endpoints.md`). Add handler/controller tests accordingly.
- New `POST logout` on the same controller (`[AllowAnonymous]`): resolve the credential like D1, call `IAuthenticationClient.RevokeJwtTokenAsync`, delete the cookie with identical attributes, return `204`.

### D3. Real revocation in the Authentication service (FR-005, SC-002)
- Reason (R3): cache eviction does not revoke because validation falls back to the signature.
- `IJwtCacheService`: add `Task RevokeAsync(string token)`. `GetAccountIdAsync` checks the denylist **first**.
  - `RedisCacheTokenService`: key `revoked:<tokenKey>` set with TTL = remaining lifetime; also delete the positive cache key. Check `KeyExists` of the denylist key before reading the cache.
  - `MemoryCacheTokenService`: `_memoryCache.Set("revoked:..", true, validTo)`; check first; remove the positive entry.
  - Obtain the token's expiry via `IJwtStorageService.GetStoredTokenAsync` (signature check) before storing; an invalid token needs no revocation.
- `authentication.proto` (both copies): add `RevokeJwtToken`. `JwtTokenGrpcService.RevokeJwtToken` calls the cache service. `IAuthenticationClient`/`AuthenticationClient`: add `RevokeJwtTokenAsync`.

### D4. CORS with credentials (FR-009)
- Replace the `AllowAnyOrigin` policy (`AddCors` "all") in `Applications/LetsTalk.Server.API/ApiServiceRegistration.cs:29`, `LetsTalk.Server.Notifications/NotificationsServicesRegistration.cs:24`, `LetsTalk.Server.FileStorage.Service/FileStorageServiceRegistration.cs:27` with a shared helper in the new project `Infrastructure/LetsTalk.Server.Cors` (`CorsServiceCollectionExtensions.cs`; own project so the ASP.NET Core framework reference does not spread to every consumer of `DependencyInjection`) that reads `Cors:AllowedOrigins` and applies `WithOrigins(...).AllowAnyHeader().AllowAnyMethod().AllowCredentials()` (+ the gRPC-web exposed headers on file storage). One helper, three callers. The helper is `AddCredentialedCors(configuration, params string[] exposedHeaders)` (policy name `all`); the `Cors` project carries the `FrameworkReference` to `Microsoft.AspNetCore.App`, and only the API, Notifications and File storage reference it. The empty-origins check runs when the CORS options are first resolved (pipeline build at startup), and only outside Development.
- File storage also has a per-endpoint override: `FileStorage.Service/Program.cs:32` `.RequireCors(cors => cors.AllowAnyHeader().AllowAnyMethod().AllowAnyOrigin())` on the gRPC mapping. It replaces the named policy for that endpoint, so it must use the same helper (named policy) or `AllowCredentials` would not apply.
- `Authentication` service keeps its policy (`AuthenticationServiceRegistration.cs:16`, `Program.cs:23,30,33`; not browser-facing).
- `appsettings.json` gets `Cors:AllowedOrigins` (empty in the committed template). Development: `appsettings.Development.json` of the API, Notifications and FileStorage services (all three exist) gets `"Cors": { "AllowedOrigins": [ "https://127.0.0.1:4200" ] }`. An origin is not a secret, so this file is committed; never put it in `appsettings.json`, which holds the owner's uncommitted secrets. Production: supplied by the deployment (environment variables `Cors__AllowedOrigins__0=https://letstalk.petukhov.fyi`). `RunAll.ps1` starts the published executables without a working directory, so ASP.NET Core does not find `appsettings.Development.json` next to them (only the explicit `AddJsonFile` for `appsettings.json` reaches the executable folder); it therefore also sets `Cors__AllowedOrigins__0=https://127.0.0.1:4200`. The Development file serves `dotnet run` and the IDE.

### D5. Notifications (FR-010)
- `NotificationHub`: add `OnConnectedAsync` per `contracts/realtime-auth.md`. Keep `AuthorizeAsync`.

### D6. File storage (FR-003)
- `JwtInterceptor`: credential = metadata `authorization` or cookie, per contract. Use `context.GetHttpContext()`.

### D7. Front end
- `services/token-storage.service.ts`: reduced to `clearLegacyToken()` (removes `auth-token` from `localStorage`, FR-007), called once at bootstrap (`APP_INITIALIZER` or in `AppComponent`).
- `interceptors/auth.interceptor.ts`: no `Authorization`; `req.clone({ withCredentials: true })` for requests to our API; on 401 clear NgRx/session state and navigate to `/sign-in` (no reload loop) (FR-008).
- New `services/session.service.ts`: `isSignedIn()` probes `ApiService.getProfile()` directly (not `StoreService.getLoggedInUser()`, which returns the NgRx-cached profile without calling the server) once at startup and once after sign-in, then caches the result; invalidated by logout/401. On session loss it also stops the SignalR connection (`SignalrService`, through a read-only `sessionLost` observable), per the spec edge case, and it dispatches `sessionActions.ended`; a meta-reducer (`state/reset-on-session-ended.meta-reducer.ts`, registered in `StoreModule.forRoot`) resets every NgRx slice, so a different account signing in on the same tab never sees the previous account`s profile, chats or messages (the page is no longer reloaded on a 401). After sign-in, if the probe fails the login component shows a message that the browser did not keep the session (FR-014). Guards `authenticated-only-guard.ts`, `anonymous-only-guard.ts`, `complete-profile-guard.ts` use it (FR-006).
- `login-by-email.component.ts`: drop `saveToken`; on `success` navigate to `chats` (the first guarded request confirms the session).
- `file-storage.service.ts`: `new FileUploadGrpcEndpointClient(url, null, { withCredentials: true })`; remove the `authorization` metadata.
- `signalr.service.ts`: `withUrl(url, { skipNegotiation: true, transport: WebSockets, withCredentials: true })`; remove `authorize()` and the `onreconnected` re-authorize; if the connection fails to start because the session is gone, treat as 401 (FR-008).
- Logout (`chat-list-top-panel.component.ts`, `account-list-top-panel.component.ts`): call generated `logout()`, then clear app state and reload.
- Regenerate `api-client/api-client.ts` (`angular.nswag`) and `API/LetsTalk.Server.API.Client/ApiClient.cs` (`csharp.nswag`).
- Environments: `environment.ts` (the local one; the outdated `environment.hosting.dev.ts` with its `development-hosting` build configuration and `build:dev:hosting` script was removed) -> all URLs `127.0.0.1:<port>`; `npm start` runs `ng serve --host 127.0.0.1 --ssl` (the `serve` target of `angular.json` now uses `buildTarget` and defaults to the `development` build configuration: no optimization, source maps on).
- `SessionService` also exposes `reloadPage()` (a one-line wrapper, so component specs can mock the reload that jsdom cannot stub).

### D8. Development environment
- `AuthCookie:Domain` empty in Development (host-only cookie, shared across ports on `127.0.0.1`). `AuthCookie:Secure` configurable; dev CORS origin is the front-end origin, `https://127.0.0.1:4200` (or `http://` if `ng serve` runs without TLS).
- **Decision (2026-10-26): all dev hosts are `127.0.0.1`, front end included.** A front end on another host such as `letstalk.local` is a different site from `127.0.0.1`, so the `SameSite=Strict` cookie would be neither stored nor sent; that setup is unsupported. Dev URLs: front end `https://127.0.0.1:4200`, API `https://127.0.0.1:5000`, Authentication `https://127.0.0.1:5001`, FileStorage `https://127.0.0.1:5003`, SignalR `https://127.0.0.1:5002` (the Notifications `appsettings.Development.json` overrides its `http` Kestrel endpoint; an environment variable cannot do it, because each service`s `Program.cs` adds `appsettings.json` from the executable folder last, and the last source wins, so the Notifications `Program.cs` also adds `appsettings.{Environment}.json` after it).
- Verified on a first run (2026-10-26): SignalR on plain `http://127.0.0.1:5002` does NOT work with an HTTPS page. The browser treats an `http` WebSocket as a different site (schemeful same-site), so the `SameSite=Strict` cookie is not sent: connections opened (`101`) but were never registered. All dev services therefore use `https`, including Notifications. `AuthCookie:Secure=false` would not help, the scheme mismatch is what blocks the cookie.

## Risks
| Risk | Mitigation |
|---|---|
| Preview features (images/links) break because the API no longer sees an `Authorization` header | D1: `GetToken()` from `Items["Token"]`; test in API `MessageController` tests; quickstart step Q6 |
| A stale cookie blocks sign-in/sign-out (JS cannot clear HttpOnly cookies) | D1 invalid-cookie rule: treat as anonymous and delete server-side; tests T020; quickstart Q15 |
| `frontend-next` proxy forwards only `authorization`, `content-type`, `accept` (`frontend-next/src/app/api/proxy/[...path]/route.ts:17`), so a cookie in the same browser never reaches the API through it | Verified; no action. Guarantees FR-004's "cookie wins" cannot silently switch its account |
| A cookie scoped to the parent domain is also sent to any other subdomain of `petukhov.fyi` | Only our services live there; if others appear, scope to the exact host and use a shared parent only where required; note in deployment docs |
| Revocation in `MemoryCacheTokenService` is per process | Authentication runs as one instance in memory mode; Redis mode is shared. Documented in the plan; no extra work |
| CSRF on state-changing calls | `SameSite=Strict` + explicit CORS origins; Origin-header check deferred to spec 002 (listed out of scope) |
| XSS can still make authenticated requests from the page | Out of scope here; reduce with CSP (separate hardening item) |
| `Secure` cookie on plain-HTTP dev | Browsers treat `127.0.0.1`/`localhost` as trustworthy; configurable otherwise |
| Production CORS origin missing from config after deploy | Startup validation: fail fast if `AllowedOrigins` is empty outside Development |
