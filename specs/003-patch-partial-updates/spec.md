# Feature Spec: Partial message updates use PATCH

**Feature folder**: `specs/003-patch-partial-updates`\
**Status**: Implemented and verified 2026-11-11 (hard switch, all three endpoints, verb only); ready to merge and deploy\
**Created**: 2026-11-11\
**Depends on**: `specs/002-short-lived-token-refresh` (merged)

## Problem
Three message endpoints change one property of an existing message and leave the rest as it is: marking a message as read, attaching a link preview, attaching an image preview. They are published as `PUT`, which means "replace the whole resource". The API contract therefore says something different from what the endpoints do, which misleads anyone reading the OpenAPI document or the generated clients.

## Goal
The API describes partial updates as partial updates (`PATCH`), and every caller keeps working after the change.

## User Stories

### US1 - The contract matches the behavior (P1)
As a developer reading the API description, I see `PATCH` for the three partial-update message operations and `PUT` nowhere on messages.
- **AS1.1** Given the OpenAPI document, then "mark as read", "set link preview" and "set image preview" are `PATCH` operations and there is no `PUT` operation on messages.
- **AS1.2** Given a request with the old `PUT` verb to any of the three paths, then it is rejected as a method that is not allowed.

### US2 - Reading a message still works (P1)
- **AS2.1** Given a message arrives in a chat I have open, when the app marks it as read, then it is marked as read exactly as before.

### US3 - Previews still arrive (P1)
- **AS3.1** Given I send an image or a link, when the cloud function or the background service finishes, then the preview appears on the message exactly as before.
- **AS3.2** Given the processing runs in the cloud function, or in the local background service (selected by configuration), then both deliver the result the same way.

## Functional Requirements
- **FR-001** "Mark as read", "set link preview" and "set image preview" MUST be exposed with the `PATCH` verb. Paths, request shapes, responses, authentication and validation stay as they are.
- **FR-002** The old `PUT` verb on these three paths MUST NOT be accepted (hard switch, see Breaking change).
- **FR-003** The Angular app, the back-end API client used by the background services and the cloud functions MUST call the three operations with `PATCH`.
- **FR-004** The behavior of each operation (what is stored, who may call it, what is returned) MUST be unchanged.

## Non-Functional Requirements
- **NFR-001** No change in the authentication, origin check or cross-origin rules.

## Breaking change and migration (constitution 6)
This is a **hard switch**, chosen by the owner. The cloud functions are deployed separately from the API. Between the API release and the redeploy of both functions, image and link previews fail with "method not allowed" (the message itself is delivered; only the preview is missing, and it is not retried). Required order:
1. Merge and regenerate the clients.
2. Deploy the cloud functions (image and link preview) and the API in the same maintenance window, functions first or together.
3. Messages sent in the gap keep no preview; accepted.

The Next.js front end (`frontend-next/`) holds a generated client with the old verb but nothing calls these operations. It is left untouched (constitution 2) and must be regenerated by the owner when it starts using them.

## Edge Cases
- A message sent during the deployment gap has no preview and stays that way.
- An old browser tab running the previous Angular build calls `PUT MarkAsRead` until reloaded; the call fails and the message stays unread until the next read action.

## Success Criteria
- **SC-001** The OpenAPI document contains no `PUT` under `/api/Message`.
- **SC-002** A manual run of the quickstart shows read marking, an image preview and a link preview working, in both the local-service and the cloud-function modes.

## Out of scope
- Renaming routes or generated method names (verb only).
- Making the change backward compatible (two-step rollout was considered and rejected).
- Other controllers and `frontend-next/`.
