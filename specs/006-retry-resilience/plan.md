# Plan: Retry short-lived failures of service-to-service calls

**Spec**: [spec.md](spec.md) | **Research**: [research.md](research.md)

## Design decisions
- **D1 - One new project, `backend/Infrastructure/LetsTalk.Server.Resilience`** (and `.Tests`). It depends only on `Polly.Core`, so the Lambdas can reference it. It holds:
  - `HttpRetrySettings` (`MaxRetryAttempts` 3, `Delay` 1 s, `MaxDelay` 10 s, `AttemptTimeout` 30 s, `TotalTimeout` 100 s) and `GrpcRetrySettings` (`MaxAttempts` 4, `InitialBackoff` 1 s, `MaxBackoff` 10 s). Defaults are carried by the classes (spec 005). They sit here, not in `LetsTalk.Server.Configuration`, so the Lambdas do not pull in the configuration project and its packages (this placement is replaced by D11, which moves them to `Configuration.Models`); their validators live in `LetsTalk.Server.Configuration/Validation` as usual (one `IValidateOptions` each, registered with `AddValidatedSettings`).
  - `HttpRetryPipeline.Configure(ResiliencePipelineBuilder<HttpResponseMessage>, HttpRetrySettings, Action<RetryEvent>? onRetry)`: the one definition of FR-001 to FR-004 (the total timeout outermost, then retry, then the attempt timeout inside it). The retry predicate is public (`HttpRetryPipeline.ShouldRetry`) and tested on its own.
  - `RetryingHttpHandler : DelegatingHandler`, running a pipeline built by `Configure`. For callers without DI (the Lambdas) and for tests.
  - `RetryEvent(Attempt, Reason, Delay)`, what a repeat tells the log.
  - Not here: the gRPC `ServiceConfig` builder. It needs `Grpc.Net.Client`, which the Lambdas must not carry, so it lives in `LetsTalk.Server.Authentication.Client` (D3).
- **D2 - HTTP clients in the services (A).** `AddResilienceHandler("retry", b => HttpRetryPipeline.Configure(b, settings, log))` on:
  1. `ImageResizeRequestConsumer` (existing named client, the API callback),
  2. a **new** named client for the link-preview API callback (`LinkPreviewApiClient`), used by `LinkPreviewRequestConsumer`,
  3. `HttpClientService` (the page download), used by `DownloadService` only.
  The attachment is one shared code path, `AddHttpRetry(target)` and `AddHttpRetrySettings(configuration)` in the new project `LetsTalk.Server.Resilience.Http` (package `Microsoft.Extensions.Http.Resilience` 10.11.0; `LetsTalk.Server.DependencyInjection` stays light because `API.Core` uses it). The two services raise `Microsoft.Extensions.Http` (and, for LinkPreview, `Microsoft.Extensions.DependencyInjection`) from 10.0.11 to 10.0.13, which the package needs. The consumer gets its client from `IHttpClientFactory`. Today `LinkPreviewRequestConsumer` calls `IHttpClientService.GetHttpClient()` for both jobs; it will use the new named client for the API call (plan note in T631). Packages: `Microsoft.Extensions.Http.Resilience` in `ImageProcessing.Service` and `LinkPreview` (the latter also for the `Utility` code path unchanged).
- **D3 - gRPC (B).** A new `GrpcRetryServiceConfig.Create(GrpcRetrySettings)` in `LetsTalk.Server.Authentication.Client` builds the `ServiceConfig` of FR-007 from the generated service descriptors (never from typed strings), listing only the four safe methods. `AddAuthenticationClientServices` gets `ConfigureChannel(o => o.ServiceConfig = GrpcRetryServiceConfig.Create(settings))` on the token client (`JwtTokenGrpcServiceClient`). The login-code client has no call that may be repeated, so it gets no policy. `AddAuthenticationClientServices` is used by three services (API, FileStorage.Service, Notifications), so all three repeat; a missing section means the defaults. No resilience handler on gRPC clients (research: retries would multiply). The settings are read from `Resilience:Grpc`.
- **D4 - Repeat of the two result reports is accepted** (spec FR-005, A2): the handlers replace the preview, so the data stays right; the cost is a possible second notification. A request id or an idempotency key was considered and rejected as a change of the API contract (FR-011).
- **D5 - Lambdas (D).** In both Lambdas, `FakeHttpClientService.GetHttpClient()` returns `new HttpClient(new RetryingHttpHandler(new HttpClientHandler(), new HttpRetrySettings(), onRetry))`, so the report and the download both repeat. `onRetry` writes `RetryEvent.Describe(<Lambda name>)` to `context.Logger.LogWarning`; `Describe` is a new method of `RetryEvent`, because the Lambda log has no message templates. The Lambdas do not read configuration; they use the defaults (AS4.1). For tests, `FakeHttpClientService` takes optional parameters for the inner handler, the settings and the clock; the Lambda passes only `onRetry`. A new project `Infrastructure/LetsTalk.Server.Lambda.Tests` references both Lambda projects and runs the same scenarios against both.
- **D6 - Settings sections.** `Resilience:Http` and `Resilience:Grpc` in the `appsettings.json` of `LetsTalk.Server.ImageProcessing.Service`, `LetsTalk.Server.LinkPreview` (HTTP only), and, for gRPC only, `LetsTalk.Server.API`, `LetsTalk.Server.FileStorage.Service` and `LetsTalk.Server.Notifications` (the three services that call the Authentication service). They list every key with the default value. `ShippedSettingsTests` gains the two section types and the LinkPreview file (which it does not link yet); the test must accept a nested section path (`Resilience:Http`).
- **D7 - Logging.** The retry callback logs through a `[LoggerMessage]` method (`Retry {Target}: attempt {Attempt} after {Reason}`), where `Target` is the client name and `Reason` the exception type or `HTTP {status}`. No address, no headers (FR-010). gRPC retries are not logged by the library; the `Grpc.Net.Client` category logs them at debug level, which is documented in the quickstart and enough for this feature.
- **D8 - Breaker and rate limiter are left out** (FR-006, research row A).
- **D9 - Cancellation** passes through: the Polly pipeline sees the caller's token and stops without a retry (FR-004).
- **D10 - The debug-only certificate bypass is removed** from the clients this feature touches: the three named HTTP clients (`ImageResizeRequestConsumer`, `LinkPreviewApiClient`, `HttpClientService`) and the two Authentication gRPC clients. Each had a `ConfigurePrimaryHttpMessageHandler` that accepted any server certificate in `DEBUG` builds; it was redundant (owner's decision, made after the phases of this plan). The clients keep the default handler, so they now require a trusted certificate in every build, and the retry setup (`AddHttpRetry`, the gRPC `ServiceConfig`) is unchanged.
- **D11 - Settings classes move to a new project `LetsTalk.Server.Configuration.Models`** (phase 6; owner's decision after the review of the pull request). Convention: classes mapped to configuration sections live with the other settings (`KafkaSettings` and the rest of `Configuration/Models`), not in the feature project. Problem that put them in `Resilience` (D1): the Lambdas must reach `HttpRetrySettings` without `LetsTalk.Server.Configuration`, which brings the `Microsoft.Extensions` configuration, DI and options packages and `Configuration.Abstractions` (with `Persistence.Enums`) into the Lambda packages. The 20 classes of `Configuration/Models` have no `using` and no dependency, so they can form a project of their own with no package and no project reference:
  - New `backend/Infrastructure/Configuration/LetsTalk.Server.Configuration.Models` (and no test project of its own: plain properties; `Configuration.Tests` keeps covering the defaults). It holds the 20 existing classes (moved with `git mv`) plus `HttpRetrySettings` and `GrpcRetrySettings`. The namespace stays `LetsTalk.Server.Configuration.Models`, so the 130 files that use it do not change; the two retry classes change namespace from `LetsTalk.Server.Resilience`, and their `using` lines are updated.
  - `LetsTalk.Server.Configuration` references `Configuration.Models` (so the 22 projects that reference it get the classes as before) and drops its reference to `Resilience`. Validators, `Services`, `ConfigurationHelper` and the registration classes stay in `Configuration`; the split of a separate `Validation` project was considered and rejected: the Lambdas never use validators, so it would add a project and solve nothing.
  - `LetsTalk.Server.Resilience` references `Configuration.Models` and keeps `Polly.Core` as its only package; the two Lambdas get the classes through it.
  - Guard: a test in `Lambda.Tests` fails if an assembly of the two Lambdas (or `Resilience`) references `LetsTalk.Server.Configuration` or `Microsoft.Extensions.Options`, so the Lambda packages cannot grow again by accident.
  - Behaviour, settings keys, defaults and validators do not change (FR-009, spec 005).

## Constitution check
- 1 Security first: no secrets are added; the log line carries neither address nor tokens (FR-010).
- 2 Generated code: `ApiClient.cs` and the gRPC stubs are not touched.
- 3 Provider-neutral persistence and registration: no persistence change. The attachment to the named clients is `HttpRetryServiceCollectionExtensions` (rule of principle 3) in `LetsTalk.Server.Resilience.Http`; the services only call it. Deviation: one more small project than D1 planned, so `DependencyInjection` and `Configuration` do not take the Http.Resilience package.
- 4 Test-first: every task group lists its tests before the code.
- 5 Front end untouched. 6 No contract change (FR-011). 7 This folder is committed before the code.
- Deviation (removed by D11): the two settings classes lived in the new `Resilience` project, not with the other settings (D1, reason: Lambdas). They move to `Configuration.Models`; their validators stay in `Configuration`.
